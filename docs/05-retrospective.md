# 05 复盘：最难的问题、收获与下一步

## 1. 三个最难的问题

### 1.1 「防重复」和「可重新排期」是一对矛盾

最初我把幂等键设计成「请求指纹」，于是遇到一个尴尬：运营改了占用时段、重新提交**完全相同**的请求，按幂等应该返回旧草稿，但业务上希望排期跟着变化走。

最后拆成两个概念才理顺：

- **幂等单元 = 素材 × 日期 × 时段 × 频道**。落在同一格就是同一份草稿实体，重复提交只会 `duplicate`。
- **方案变更 = 换格子**。新格子生成新草稿，旧草稿标 `superseded` 并记录 `superseded_by`，活跃草稿回到 1 份。

这样「相同请求只产生一份草稿」（E05）与「更换占用时段重新提交」（E09）可以同时成立，而且历史方案没丢。

### 1.2 「模型说了」不等于「系统发生了」

这是本题最容易失分的地方。我的第一版把模型 final 里的 `save_status` 直接写进报告，于是只要模型一句话就能「保存成功」——哪怕它根本没调用工具，甚至草稿库是空的。

三层解法的核心是**把事实与声明分开**：

1. 工具返回值写进事实台账（facts），报告只从台账渲染；
2. 模型声明只当「主张」，由 `verifier` 逐条比对台账，不一致就降级并记 `critical`；
3. `published` 字段在渲染层写死为 `False`，且系统里根本没有发布工具 —— 从结构上消灭这类错误，而不是靠提示词。

E10 那个「一步都不调用工具、直接宣称已保存已发布」的对抗用例，就是为这条防线准备的。

### 1.3 让模型「看结果再调整」，又不让它乱来

冲突处理如果全交给代码（代码选时段），就退化成固定流程；全交给模型，它可能把草稿排进别人的时段或者悄悄改掉合同约定的时间。

我的切分是：**判断归模型，边界归代码**。

- 模型可以做：决定查什么、要不要补查、要不要换时段、换哪个、要不要升级待确认。
- 代码坚持：硬性时间不可改、block 素材不入库、时段被占不许写、幂等键不可伪造、步数与调用次数有上限。

题面里「未经用户同意不得擅自改变硬性发布要求」这句话，最后落成了 `POLICY_HARD_CONSTRAINT` 这个工具层拒绝，而不是提示词里的一句叮嘱。

## 2. 收获

1. **Agent 项目的质量上限由「可验证性」决定**。同样是 ReAct，能不能证明「它是因为看到了冲突才改时段」，比能不能跑通重要得多。trace 里记 `rationale` + 工具参数 + 观察摘要，评审才能抽查。
2. **评测要和产物共用一份断言**。我把 `expect` 写在用例里，CLI `replay` 与 `tests/test_scenarios.py` 共用同一个 `check_case_expectations`，所以「examples 里的产物过期」这件事会被测试直接抓出来。
3. **失败路径比成功路径更能体现工程水平**。步数上限、保存失败、工具超时、模型说谎这四条，我花的时间比正常排期多，但它们才是评分项。
4. **零依赖是给评审的体验分**。评审 clone 下来 `python -m unittest discover -s tests` 就能跑，不需要装任何东西，比多写两个功能更有价值。
5. **写文档时被迫发现设计漏洞**。写「冲突调整语义」那节时才意识到候选排序默认「距离优先」会让 17:00 排在 19:00 前面，回头改了 `slots.py`。

## 3. 下一步

按优先级：

1. **确认流闭环**：待确认项现在只能「记下来」，没有回写通道。下一步做 `confirm_draft(draft_id, confirmed_by)`，把 `pending_confirmation` → `confirmed`，并在草稿里记录确认人与时间。
2. **批量与拆单**：一个工单多条素材时，先按规则过滤，再在时段配额内做分配（这属于组合优化，可以先用贪心 + 冲突回退）。
3. **supersede 的并发安全**：现在是「扫描目录 → 改写标记」，多实例并发下可能漏标。改成目录级锁文件或者单文件索引。
4. **真实模型评测集**：现在只有 2 条真实 trace。下一步跑满 11 个用例 × 3 次，统计「合规率 / 需人工纠正率 / 平均步数」，把结论从「能跑」变成「跑得稳」。
5. **规则外置到配置服务**：现在规则阈值在 JSON 里，改一次要重新部署；生产上应该是配置中心 + 版本化。
