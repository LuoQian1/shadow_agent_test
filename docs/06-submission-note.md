# 06 提交说明：题目、思路与验收对照

> 这篇是给评审的「一页纸」：题目到底要什么、我怎么理解、怎么实现、怎么证明。
> 详细设计见 `02-solution.md`，实测数据见 `03-evaluation.md`。

## 1. 题目要点（题三）

> 帮助内容团队找出待处理素材，形成**无冲突、可确认的发布排期**。
> 提供素材读取、规则检查、时段查询、排期草稿保存四类工具；
> 输出每项素材的审核状态、风险原因、建议时段、待确认项、草稿保存状态；
> **仅保存草稿，不接真实发布**；未经用户同意不得擅自改变硬性发布要求。

必须验收：正常排期、素材信息缺失、规则风险、时段冲突、重复提交、保存失败。
参考实例：M01 无风险、用户要 18:00、该时段已占用、19:00 可用 →
建议 19:00 并标记待确认，**不得称为已发布**。

## 2. 我的理解：难点不在「跑通」，在「边界」

题面把评分依据写得很直白 —— **冲突调整、确认边界、防重复**，并明确「越权发布或虚报保存成功属于关键缺陷」。所以我把它当成一个**信任边界**问题来做，而不是一个排期算法题：

1. **模型可以判断，但不能越权。** 换不换时段、要不要补查、要不要升级给人，交给模型；
   改硬性时间、把草稿存进别人的时段、跳过阻断规则，由代码直接拒绝。
2. **模型的「说法」不等于「事实」。** 报告里的保存状态、草稿 ID、发布状态只能来自工具台账，
   模型嘴里说的「已保存 / 已发布」要被校验层逐条核对、必要时打回。
3. **重复提交必须收敛。** 幂等键由代码派生（不能被模型换掉），写入用文件系统原子操作。
4. **没跑完就说没跑完。** 步数 / 工具调用有上限，触达即返回明确的未完成状态。

## 3. 整体思路

```
工单 + 素材 + 已有排期 + 草稿库
        │
        ├── 规则引擎（10 条，review / scheduling 两类）
        └── 时段规划（占用 + 禁发 + 间隔 + 配额）
                    │
        ┌───────────▼───────────┐
        │  ReAct 循环（模型驱动）│  ← 每轮只看一个 JSON 动作，观察结果回灌
        │  read → brief → 规则   │
        │  → 补查 / 查时段       │
        │  → 保存草稿 → 收尾     │
        └───────────┬───────────┘
                    │ 事实台账（facts）
        ┌───────────▼───────────┐
        │ 声明校验 verifier      │  谎报保存/发布 → 降级 + 记 critical
        │ 渲染 renderer          │  报告只从台账生成，published 恒为 false
        └───────────────────────┘
```

四层防线各管一段，互不替代：

| 层 | 位置 | 拦住什么 |
| --- | --- | --- |
| L1 能力边界 | 工具注册表 | 系统里没有 `publish` / `confirm` 工具，越权发布结构上不可能 |
| L2 策略拒绝 | `save_schedule_draft` | 改硬性时间、block 素材入库、资料缺失入库、排进已占用时段 |
| L3 幂等原子写 | 草稿库 | 重复提交只留一份草稿（8 线程并发也只成功一次） |
| L4 声明校验 | `verifier` | 谎报「已保存 / 已发布」、审核状态放水、建议违背硬性要求 |

## 4. 关键决策与理由

| 决策 | 理由 |
| --- | --- |
| 原生实现，不用 LangGraph / ADK | 得分点是可验证性（步数上限、幂等、trace）。框架会把这些藏进内部，评审看不出是谁实现的 |
| 纯标准库 + `unittest` | 评审 `git clone` 后零安装即可跑，旧 Python（3.8）也能跑 |
| 硬性时间由**工具层**拒绝，不靠提示词 | 提示词管不住模型；`POLICY_HARD_CONSTRAINT` 是硬的 |
| 幂等键 = `sha256(素材|日期|时段|频道)` | 模型若能自定义 key，换个 key 就能为同一请求造第二份草稿 |
| 同一素材换时段 → 旧草稿 `superseded` | 活跃草稿只能有一份，但历史方案不能删（要可审计） |
| 冲突后**优先顺延、其次提前** | 提前发往往来不及预热；这条让 E02 建议 19:00 而不是 17:00 |
| `null` = 资料缺失，`false` = 无授权 | 把「信息缺失」和「规则风险」两个验收点彻底分开 |
| 冲突算 `scheduling`，不算素材风险 | 否则「素材无风险但有冲突」会被渲染成「素材有风险」，与题意不符 |

## 5. 六个必验场景怎么过的

| 场景 | 用例 | 实际结果 |
| --- | --- | --- |
| 正常排期 | E01 | 审核 pass，草稿落在请求的 10:00 |
| 素材信息缺失 | E03 | 先补查素材服务，仍缺 → `missing_info`，**不保存草稿** |
| 规则风险 | E04 | 无肖像授权 + 极限词 → `blocked`，列出 R03/R04，无草稿 |
| 时段冲突 | E02 | 18:00 被 M09 占 → 建议 19:00 → `pending_confirmation` → 未发布 |
| 重复提交 | E05 | 同一请求跑两次：`saved` → `duplicate`，**同一 draft_id，草稿数 1** |
| 保存失败 | E06 | 注入 2 次 EACCES，重试一次仍失败 → 明确 `failed`，退出码 2 |
| 不得改硬性要求 | E07 | 硬性 18:00 被占 → 不保存、不给替代时段、升级待确认 |
| 防越权 / 防虚报 | E10 | 假模型谎报「已保存 + 已发布」→ 校验层打回，记 critical |

每个用例都带 `input.json`（输入）、`actual_output.json`（结构化输出）、
`report.md`（人读运行记录）、`trace.jsonl`（逐步动作与观察）。

真实模型（`deepseek-flash`）跑了 E02、E03 两条路径，记录在
`examples/traces/real/`：两条的动作序列不同，且都是**看到工具返回后才改动作**
（E02 是查到占用才改时段，E03 是补查为空才收尾），这是 ReAct 而非固定流程的证据。

## 6. 怎么运行

```bash
git clone https://github.com/LuoQian1/shadow_agent_test
cd shadow_agent_test

python -m unittest discover -s tests -v      # 111 个测试，零安装
python -m src.cli replay --model offline     # 11 个场景全跑 + 自检断言
python -m src.cli run --case examples/cases/E02_slot_conflict/input.json --model offline
```

需要真实模型时：`cp .env.example .env` 填 `OPENAI_API_KEY`，把 `--model` 换成 `real`。

## 8. 已知限制（不藏）

1. 离线策略模型只验证流程与护栏，**不代表真实模型决策效果**；真模型只有两条单次采样。
2. 一次只处理一条素材。
3. 补查 / 排期 / 发布均为本地 mock，无真实第三方服务与时区处理。
4. `supersede` 的扫描-改写非事务，多实例并发下可能漏标（单实例有测试保障）。
5. 规则与数据为合成数据（10 条规则、5 个黑名单词）。
